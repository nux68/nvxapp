APPLICATIVI E CONTESTI
======================
nvxapp e' multi-applicativo. Le tabelle comuni stanno in public, quelle di ogni applicativo
in un contesto dedicato. Gli applicativi sono l'enum ApplicationType
(nvxapp.server.data/Infrastructure/Tenancy/ApplicationType.cs):
    0 Common                -> CommonDbContext              (Infrastructure) dati comuni dell'azienda, SEMPRE presenti
    1 Moke                  -> MokeDbContext                (Infrastructure)
    2 AttendanceTracking    -> AttendanceTrackingDbContext  (ramo AttendanceTracking)
    3 Crm                   -> CrmDbContext                 (ramo CRM)
    4 DocumentManagement    -> DocumentManagementDbContext  (ramo DocumentManagement)

COMMON (dati comuni dell'azienda, vedi nvxapp.server/docs/ANALISI_CRM_APPLICATIVO.md [branch CRM] §2)
    Tabelle condivise tra gli applicativi: Az_Anagrafica (una riga per azienda), Az_Cliente, Az_ClienteContatto,
    Dip_Anagrafica (utente facoltativo), Az_Sedi, Az_SediReparto, Par_Competenza, Dip_Competenza, Dip_RapportoAutovetture.
    Le entita' comuni sono partial: un ramo puo' aggiungere navigazioni verso le proprie tabelle, che CommonDbContext ignora.
    Non si attiva in CompanyApplication: lo schema tenant_<IdAzienda>_0 esiste per ogni azienda ed e' migrato
    per primo (gli applicativi hanno chiavi esterne verso le sue tabelle).
    Gli applicativi le mappano con ExcludeFromMigrations() SENZA schema (sola lettura): il search_path dei loro
    contesti e' "tenant_<IdAzienda>_<App>", "tenant_<IdAzienda>_0", public. Le scritture passano dai servizi
    comuni (ClientServer-Service/infrastructure/Common) e dai repository Repositories/Tenant/Common.

PublicDbContext         -> tabelle comuni, sempre in public
                           (Identity, Dealer, FinancialAdvisor, Company, User*, AppSetting, CompanyApplication)
                           cartella Migrations/Public   storico public."__EFMigrationsHistory"

<Applicativo>DbContext  -> tabelle dell'applicativo
                           cartella Migrations/<Applicativo>   storico "__EFMigrationsHistory_<Applicativo>"

Le migration degli applicativi NON contengono il nome dello schema: lo decide la connessione (search_path).
    modalita' singola       -> tutte le tabelle in public
    modalita' multi-tenant  -> uno schema per azienda e applicativo: tenant_<IdAzienda>_<IdApplicativo>
                               (es. azienda 5 con applicativi 1 e 2: public, tenant_5_0, tenant_5_1, tenant_5_2)
Le stesse migration valgono per entrambe le modalita': NON vanno modificate a mano.

Regole:
  - un nome di tabella appartiene a UN solo contesto (in modalita' singola stanno tutte in public):
    l'avvio si ferma se trova duplicati
  - le tabelle di un applicativo possono riferire tabelle di public (mappate con schema "public"
    + ExcludeFromMigrations) e di Common (mappate SENZA schema + ExcludeFromMigrations),
    MAI tabelle di un altro applicativo
  - le tabelle di public NON possono riferire tabelle di un applicativo
  - una migration riguarda un solo contesto (indicare sempre --context)

Nuovo applicativo:
  1. aggiungere il valore all'enum ApplicationType (il numero non va mai cambiato)
  2. creare <Applicativo>DbContext : ApplicationDbContextBase e la sua design-time factory
  3. registrarlo con services.AddApplicationDbContext<...>(ApplicationType.X) nell'installer del modulo
  4. gli inizializzatori del modulo dichiarano Application = ApplicationType.X
  5. creare la migration iniziale (vedi sotto)


ATTIVAZIONE DEGLI APPLICATIVI PER AZIENDA
=========================================
Tabella public."CompanyApplication". Nessun applicativo e' attivo di default.
API: api/CompanyApplication/CompanyApplicationList   { idCompany }
     api/CompanyApplication/CompanyApplicationPut    { idCompany, applicationType, active }
  - attivazione: crea/migra lo schema (multi-tenant) ed esegue gli inizializzatori dell'applicativo
  - disattivazione: blocca l'accesso, schema e dati restano (riattivando si ritrova tutto)
L'accesso ai dati di un applicativo non attivo e' rifiutato in entrambe le modalita'.
UserLoad restituisce userData.activeApplications.


MODALITA' MULTI-TENANT
======================
appsettings: DbParameter:MultiTenant (true/false)
Si decide al PRIMO avvio su un database vuoto: viene salvata in public."AppSetting" (TenancyMode)
e non si puo' piu' cambiare. Se la configurazione non coincide l'applicazione non parte.

All'avvio (DatabaseInitializer):
  0. verifica che nessuna tabella sia in due contesti
  1. migra PublicDbContext
  2. verifica/salva la modalita'
  3. migra gli applicativi: in public (singola) oppure ogni schema azienda/applicativo ATTIVO (multi),
     creando lo schema se manca


crea  (sostituire <Nome>)
dotnet ef migrations add <Nome> --context PublicDbContext -o Migrations/Public --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef migrations add <Nome> --context CommonDbContext -o Migrations/Common --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef migrations add <Nome> --context MokeDbContext -o Migrations/Moke --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef migrations add <Nome> --context AttendanceTrackingDbContext -o Migrations/AttendanceTracking --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef migrations add <Nome> --context CrmDbContext -o Migrations/Crm --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef migrations add <Nome> --context DocumentManagementDbContext -o Migrations/DocumentManagement --project nvxapp.server.data --startup-project nvxapp.server

aggiorna db
Normalmente NON serve: le migrazioni vengono applicate all'avvio dell'applicazione (tutti gli schemi).
Solo per lo sviluppo in modalita' singola:
dotnet ef database update --context PublicDbContext --project nvxapp.server.data --startup-project nvxapp.server
dotnet ef database update --context MokeDbContext --project nvxapp.server.data --startup-project nvxapp.server

cancella (ultima migrazione non ancora applicata)
dotnet ef migrations remove --context <Contesto> --project nvxapp.server.data --startup-project nvxapp.server

lista delle migrazioni
dotnet ef migrations list --context <Contesto> --project nvxapp.server.data --startup-project nvxapp.server
